§0Übersicht & Motivation

Der Redactor erkennt heute Secrets über (a) eingebaute Regex-Patterns (OpenAI/Anthropic-Keys, JWTs, PEM-Blöcke, …) und (b) eine User-Keyword-Liste in ~/.config/redactor/keywords.txt. Sensitive Pfade (.env, .ssh/*, .aws/credentials) sind hardcoded im Path-Guard.

Dieses Spec führt eine zweite Sicherheitsstufe ein:

  • ~/.redactorignore — ersetzt keywords.txt vollständig. Eine einzige globale gitignore-style-Datei für persönliche Keywords und Pfade. Self-protected: Tools können sie weder lesen noch editieren.
  • Default-Blocks für Office-Docs & Crypto-Container — .xlsx, .docx, .pdf, .kdbx, .gpg etc. werden ohne Konfiguration geblockt, weil Read-Tool sie nicht sinnvoll parsen kann oder weil sie per Definition Secrets enthalten.
  • Project-Level Unlock via .redactor.toml [allow] — pro Projekt kann ein User Default-Blocks oder User-Pfade gezielt freischalten (z.B. Test-Fixtures).
  • ML-basierter Klassifikator — neuer Subcommand redactor classify-files <dir> nutzt Microsoft Presidio + GLiNER (multilingual PII-Modell) via Python-Sidecar, um sensitive Dateien automatisch zu erkennen. Output landet in ~/.redactorignore.suggested für manuelle Review; redactor classify-merge übernimmt den interaktiven Übertrag.

Kern-Tradeoff dieses Specs

Komplexität +: Python-Sidecar mit ~1 GB ML-Modellen ist eine signifikante Architektur-Erweiterung. uv-managed venv, Lifecycle-Subcommands (install/update/uninstall), Cross-Plattform-Pflege.

Sicherheit +: Personalisierte Geheimnislisten + ML-Klassifikation decken Lücken ab, die Regex-only nicht erreichen kann (Steuerdokumente, Personalakten, Versicherungsdaten).

Mitigation: Sidecar ist strikt optional — Path-Guard und .redactorignore funktionieren ohne Python. classify-files ist der einzige Code-Pfad, der den Sidecar braucht.

2.2 Heuristik: Keyword vs. Pfad

Jede Nicht-leere, Nicht-Comment-Zeile wird durch folgende Regeln klassifiziert (Reihenfolge wichtig):

oder Glob-Char

(globset)"] Detect -->|no| Kw["→ Keyword

Edge-Case: Keyword das ein / enthält

Z.B. URL-Snippet example.com/internal-path würde fälschlich als Pfad geparst. Workaround: explizites Quoten — "example.com/internal-path" wird IMMER als Keyword behandelt. Implementiert via Anführungszeichen-Stripping vor der Heuristik.

Existierender Path-Guard (unverändert): *.env, .envrc, id_rsa*, .ssh/* (außer known_hosts), .aws/credentials, .aws/config, **/*.pem, **/*.key, **/secrets/**

§3Self-Protection & Project-Level Unlock

3.1 Self-Protection für ~/.redactorignore

Hardcoded in hook.rs path-guard:

fn is_self_protected(path: &Path) -> bool {
    let canonical = path.canonicalize().unwrap_or_else(|_| path.to_path_buf());
    let home_ignore = dirs::home_dir().unwrap().join(".redactorignore");
    canonical == home_ignore.canonicalize().unwrap_or(home_ignore)
}

Aufgerufen aus drei Hook-Subcommands:

  • pre-read — checkt tool_input.file_path
  • pre-bash — checkt alle pfadähnlichen Argumente (existierender Code)
  • pre-edit (NEU) — matcher Edit | MultiEdit | Write, checkt tool_input.file_path

Warum pre-edit trotz Read-Block-Indirection?

Edit und MultiEdit verlangen in Claude Code einen vorherigen Read — wenn Read geblockt ist, sind sie indirekt mitgeblockt. Write kann jedoch neue Files anlegen, ohne vorher zu lesen. pre-edit ist primär dafür da, dass z.B. Write(~/.ssh/config, …) oder Write(~/.redactorignore, …) nicht stillschweigend einen geschützten Pfad anlegen.

Edit/MultiEdit im selben Matcher sind defense-in-depth — falls Claude Code's Read-Before-Edit-Invariante irgendwann fällt.

3.2 Project-Level Unlock

Im Repo-Root eines Projekts kann eine .redactor.toml (existiert bereits) gezielte Ausnahmen definieren:

# <project>/.redactor.toml

[[patterns.custom]]
name = "internal_id"
re = 'INT-\d{6}'

[whitelist]
# (existing) skip Secret-Detection-Patterns innerhalb dieser Files
paths = ["docs/example.cfg"]

# NEU — File-Read-Unlocks
[allow]
paths = [
    "fixtures/sample-customer.xlsx",
    "fixtures/**/*.docx",
    "data/test-fixtures/*",
]
filetypes = ["xlsx", "docx"]   # default-blocks dieser Typen aufheben

§4classify-files Subcommand

4.1 CLI-Oberfläche

# Grundform
redactor classify-files <directory>

# Mit Optionen
redactor classify-files ~/Documents/ \
    --max-depth 3 \
    --max-file-size 10MB \
    --threshold 0.7 \
    --output ~/.redactorignore.suggested \
    --format text         # text | json | yaml
    --apply               # shortcut: skip review, direkt anhängen
    --apply --yes-interactive   # synonym zum separaten classify-merge --yes

4.2 Workflow intern

  1. walkdir auf <directory>. Skip-Listen: .git/, .venv/, node_modules/, Symlinks, Hidden-Dirs, Files > --max-file-size (default 5 MB).
  2. Pre-Filter: Crypto-Container werden gar nicht erst dem Sidecar gegeben (sind eh hardcoded blockiert). Spart Latenz.
  3. Sidecar-Call: JSON über stdin/stdout an ~/.config/redactor/classifier/venv/bin/python -m classify. Pro File: {path, filename, size, content_preview} (erste 4 KB UTF-8-lossy).
  4. Threshold-Filter: nur Results mit confidence ≥ --threshold übernehmen.
  5. Output: Suggestions-Datei schreiben (Default ~/.redactorignore.suggested), Summary auf stderr.

4.3 Format der .suggested-Datei

# redactor classify-files — suggestions
# generated: 2026-05-12T22:45:01+02:00
# input:     /Users/alice/Documents
# files:     1247 scanned, 89 above threshold
# threshold: 0.6

# confidence=0.92  labels=TAX_DOC,FINANCIAL_RECORD
# evidence="Erkennung: Einkommensteuer (0.94), Finanzamt (0.91)"
/Users/alice/Documents/Steuer/2024/erklaerung.pdf

# confidence=0.88  labels=PERSONAL_RECORD,NAME_LIST
# evidence="14 person names detected by GLiNER"
/Users/alice/Documents/Kontakte/familienliste.txt

# confidence=0.81  labels=CREDENTIAL,PRIVATE_KEY
# evidence="contains BEGIN OPENSSH PRIVATE KEY block"
/Users/alice/Backups/old-keys/id_rsa.bak

4.4 Merge-Helper

# Interaktiv: yes/no/skip-rest pro Zeile
redactor classify-merge ~/.redactorignore.suggested

# Non-interaktiv (vertraut der ML komplett)
redactor classify-merge ~/.redactorignore.suggested --yes

# Dry-run
redactor classify-merge ~/.redactorignore.suggested --dry-run

Schreibt nach ~/.redactorignore, dedupliziert gegen existierende Einträge, behält bestehende Comments unverändert. Comments aus .suggested werden nicht mitkopiert.

§7Testing-Strategie

7.1 Rust-Tests

tests/redactorignore_parsing.rs
  • Heuristik Keyword vs. Pfad (gitignore-Syntax)
  • Comments und blank lines werden gestrippt
  • Negation (!path) korrekt erkannt
  • Globs (**, ?, [abc]) als Pfad klassifiziert
  • Edge: leere Datei, BOM-Header, CRLF line endings, riesige Datei (10 000 Zeilen)
  • Edge: Keyword mit explicit quoting ("foo/bar")
tests/path_guard_integration.rs
  • Hardcoded blocks immer aktiv (.env, .kdbx, …)
  • Pfade aus .redactorignore blockiert
  • ~/.redactorignore selbst self-protected
  • [allow] in .redactor.toml überschreibt Office-Doc-Defaults
  • [allow] überschreibt nicht Crypto / .env / self-protect
  • Precedence-Reihenfolge wie §3.3 spezifiziert
tests/classify_files_smoke.rs
  • Leeres Verzeichnis → exit 0, leere .suggested
  • Skip-Patterns (.git/ etc.) respektiert
  • Crypto-Container werden nicht an Sidecar geschickt (vorab Skip)
  • --max-file-size cuttet große Files ab
  • Sidecar fehlt → Exit 2 mit klarer Fehlermeldung (mock via REDACTOR_CLASSIFIER_PATH=/nonexistent)

§PUmsetzungsplan (Phasen)

Implementation in 5 inkrementellen Phasen — jede für sich mergeable und nutzbar. Geschätzte Größenordnungen: S = ≤ 200 LOC, M = 200-500, L = 500-1000.

Phase 1 .redactorignore Parser + Path-Guard-Integration Size: M
  • Neues Modul src/ignorefile.rs mit Parser + Heuristik + Glob-Compiler
  • config.rs erweitert: lädt ~/.redactorignore, fällt zurück auf legacy keywords.txt mit Warning
  • hook.rs path-guard: lädt Pfade aus .redactorignore + self-protect
  • Office-Doc + Crypto Default-Blocks hardcoded ergänzt
  • Tests: redactorignore_parsing.rs
  • Docs: README.md Section "Personal sensitivity list"

Akzeptanzkriterien: User kann .redactorignore anlegen, Keywords erscheinen als <redacted:keyword>, Pfade in der Liste werden bei Read/Bash blockiert, ~/.redactorignore selbst ist via Hooks nicht lesbar.

Phase 2 pre-edit Hook + Project-Level [allow] Size: S
  • Neuer Subcommand redactor hook pre-edit
  • .redactor.toml Parser erweitert um [allow]-Section
  • Path-Guard checkt [allow] mit Precedence-Reihenfolge aus §3.3
  • examples/strict-redaction/claude/settings.json bekommt pre-edit-Matcher
  • Tests: path_guard_integration.rs erweitert mit [allow]-Szenarien

Akzeptanzkriterien: Write-Tool kann keine geschützten Pfade neu erstellen. Project-[allow] kann Office-Doc-Defaults und User-.redactorignore-Pfade per Glob freischalten — aber NIE Crypto/.env/.redactorignore-self.

Phase 3 Python Sidecar Skeleton + classifier-install Size: L
  • classifier-py/-Verzeichnis im Repo mit pyproject.toml
  • classify/__main__.py liest JSON-Request, schreibt JSON-Response (Stub: alle Files mit confidence=0)
  • Rust-Module src/classify.rs: IPC mit Sidecar via stdin/stdout
  • Subcommand classifier-install: uv venv + uv pip install + Model-Download
  • Subcommands classifier-status, classifier-uninstall
  • config.toml + labels.txt mit Defaults erstellt

Akzeptanzkriterien: classifier-install läuft End-to-End auf frischem Mac (uv vorausgesetzt). Sidecar antwortet auf JSON-Request mit Stub-Response. Disk-Footprint ≤ 600 MB.

Phase 4 Echte Klassifikation (Presidio + GLiNER) + classify-files Size: L
  • classify/analyzer.py: Presidio mit GLiNER als Custom Recognizer wired up
  • File-Aggregation: aus Entity-Counts + Filename-Signals → Confidence pro File
  • Subcommand classify-files: walkdir, Skip-Filter, Sidecar-Call, Threshold-Filter, .suggested-Output
  • Tests: classify_files_smoke.rs, test_analyzer.py
  • Docs: README.md Section "ML-based file classification"

Akzeptanzkriterien: classify-files ~/Documents/ liefert für deutsche Steuerdokumente, Personalakten, Crypto-Backups Confidence ≥ 0.7. Latenz ≤ 30 s pro 100 Files auf M4.

Phase 5 classify-merge + migrate-keywords + Polish Size: M
  • classify-merge (interaktiv + --yes + --dry-run)
  • migrate-keywords Helper
  • classifier-update
  • knowledge/decisions.md mit 3 neuen Entscheidungen ergänzt

§DEntscheidungs-Log

Drei Architektur-Entscheidungen werden in knowledge/decisions.md als neue Einträge dokumentiert (mit Datum 2026-05-12 und einer Verweis-Section auf dieses Spec):

D-1 — Python-Sidecar statt Rust-native ML

Entschieden: ML-Klassifikation wird via Python-Subprocess (Presidio + GLiNER + spaCy) gemacht, nicht via Rust-native Inferenz (z.B. candle, burn).

Begründung: Presidio liefert produktionsreife PII-Aggregation und Confidence-Scoring out-of-the-box. Equivalent in Rust nachzubauen = mehrere Wochen Arbeit ohne klaren Mehrwert. GLiNER + spaCy haben weder offizielle noch stabile Rust-Bindings. Der Sidecar ist optional — nur classify-files braucht ihn.

Trade-off: +1 Python-Dependency (uv vorausgesetzt), +550 MB Disk-Footprint. Akzeptiert.

D-2 — Neue [allow]-Section, nicht [whitelist] erweitern

Entschieden: Project-Level File-Unlocks landen in einer neuen [allow]-Section in .redactor.toml, nicht in der existierenden [whitelist].

Begründung: [whitelist] bedeutet heute "skip pattern detection in this file" — semantisch eine andere Achse als "allow read/edit of this path". Overloading würde Verwirrung produzieren ("warum wird mein File nicht redacted, ich hab's doch in [whitelist] …"). Klare Trennung von Names: [whitelist] = Content-Skip, [allow] = File-Access-Override.

D-3 — urchade/gliner_multi_pii-v1 als Default-Modell

Entschieden: Default-Model für GLiNER ist urchade/gliner_multi_pii-v1. User kann via config.toml zu beliebigem GLiNER-Modell wechseln.

Begründung: Explizit auf PII fine-tuned, multilingual inkl. Deutsch, ~350 MB (passt auf jede SSD), MPS-fähig auf Apple-Silicon. Bessere Out-of-the-Box-Qualität als gliner_multi-v2.1 für unseren PII-Detection-Use-Case.

Re-evaluate when: Ein neueres Modell mit deutlich besseren PII-Metriken erscheint (Watch: HuggingFace-Trending alle 6 Monate).

§?Offene Punkte / TBD

Punkte, bei denen das Spec eine Default-Entscheidung trifft, aber die User-seitig in der Implementation noch geprüft werden sollten:

  1. Default-Threshold für classify-files ist 0.6 — Wert wird in Phase 4 anhand realer Files empirisch nachjustiert werden müssen. Initial: 0.6, dann beobachten.
  2. Default-Skip-Patterns könnten je nach Verzeichnis aggressiver sein (z.B. **/__pycache__/**, **/target/**). Aktuell minimal — Erweiterung wenn Praxis es zeigt.
  3. Sidecar-Cold-Start-Latenz (~5-10 s zum Modell-Laden) — sollten wir einen --keep-warm-Modus überlegen, der den Sidecar als Daemon hält? Aktuell: nein (YAGNI), aber Punkt für Phase 4 Review.
  4. Windows-Support für Sidecar: uv läuft auf Windows, GLiNER/Presidio in der Theorie auch. Manuelle Verifikation erst in Phase 5.

§VPhase-5 Windows-Verifikation & Bug-Fixes (2026-05-13)

Schließt den offenen Punkt 4 aus §? ("Windows-Support manuelle Verifikation erst in Phase 5"). Während des End-to-End-Tests auf Windows 11 (PowerShell + Git Bash, uv 0.11.7, Python 3.14.4) sind vier Bugs aufgefallen — alle im Lifecycle-Pfad, keiner in .redactorignore oder Path-Guard.

V.1 Bug-Übersicht

BugSymptomStelleFix
A GLiNER-Download bricht mit SyntaxError: 'unicodeescape' codec can't decode … \UXXXXXXXX ab. Python interpretiert den Windows-Pfad C:\Users\… im inline -c-Skript als Unicode-Escape. src/classifier_lifecycle.rs::download_gliner_model Helper build_gliner_script() extrahiert; Pfad wird via .to_string_lossy().replace('\\', "/") auf Forward-Slashes normalisiert. Python akzeptiert auch auf Windows Forward-Slashes in Path/os.path.
A.2 OSError: [WinError 1314] Dem Client fehlt ein erforderliches Recht beim Erstellen der HF-Cache-Symlinks (blobs/ → snapshots/). Tritt ohne Developer Mode / Admin auf jedem Windows-System auf. src/classifier_lifecycle.rs::build_gliner_script + src/classify.rs::run_classifier + classifier-py/src/classify/analyzer.py::build_analyzer Drei Änderungen koordiniert: (1) snapshot_download(local_dir=…, local_dir_use_symlinks=False) statt cache_dir= → flacher symlinkfreier Layout. (2) Neuer Helper classify::gliner_model_dir() als Single-Source-of-Truth für den Pfad. (3) Rust setzt env REDACTOR_GLINER_PATH beim Spawnen des Sidecars; Analyzer lädt via GLiNER.from_pretrained(local_path) falls gesetzt, Fallback auf repo_id (Mac/Linux Default-Pfad).
B spaCy-Modelle landen im falschen Venv: Using Python 3.14.4 environment at: C:\Users\Alice\.venv. spacy.util.is_package() im Sidecar-Venv liefert False, obwohl der Subcommand Download and installation successful meldet. src/classifier_lifecycle.rs::download_spacy_model Vor dem Command::spawn werden VIRTUAL_ENV + UV_PROJECT_ENVIRONMENT auf das Sidecar-Venv gesetzt. uv's Environment-Discovery findet sonst das nächste .venv im cwd-Tree (typischerweise ~/.venv) und installiert dort. Zusätzlich: run_install verifiziert nach erfolgreichem Exit, dass spacy.util.is_package(model) im Sidecar-Venv true ist (Defence-in-Depth).
C classifier-install --quiet druckt am Ende „classifier-install complete" und exited 0, obwohl GLiNER hart gescheitert war (nur Warning auf stderr). Status zeigt danach korrekt no für die fehlenden Komponenten — aber die Install-CLI lügt. src/classifier_lifecycle.rs::run_install run_install sammelt Failures in einem Vec<String>. Bei nicht-leerer Liste: Exit 3, klare Summary auf stderr ("classifier-install INCOMPLETE — N component(s) failed:" + bullet-Liste pro Failure + Hint auf classifier-status).

V.2 Zusätzliche Schutzschicht: Empty-Dir-Check

HuggingFace's snapshot_download nutzt intern einen ThreadPool. Bei Symlink-Fehlern wird die Worker-Exception per concurrent.futures propagiert — aber wenn der Pool sie schluckt, exited das Wrapper-Script trotzdem 0. Belt-and-Suspenders: nach erfolgreichem Exit prüft download_gliner_model, ob local_dir mindestens eine Datei enthält. Wenn nicht → harte Fehlermeldung mit „exited 0 but … is empty — likely silent failure".

V.3 Cross-Platform-Test-Cleanup

Bonus-Fix außerhalb des Specs: src/classify.rs::tests hatte ungated use std::os::unix::fs::PermissionsExt und use std::sync::Mutex als globale Test-Imports. Auf Windows brach das cargo test mit could not find 'unix' in 'os'. Mit #[cfg(unix)] pro use-Statement gegated.

V.4 Neue Tests

  • gliner_script_normalises_windows_backslashes — Regression: keine \ im Output, Forward-Slash-Pfad sichtbar.
  • gliner_script_preserves_unix_slashes — Sanity-Check: Unix-Pfade werden 1:1 übernommen.
  • gliner_script_uses_local_dir_mode_without_symlinks — Stellt sicher, dass nie wieder cache_dir= reinkommt (Symlink-Regression). Asserts: enthält local_dir= + local_dir_use_symlinks=False + nicht cache_dir=.

V.5 Disk-Usage-Update

Disk-Footprint: ~1.9 GB statt geplant ~550 MB

Konsequenz aus dem local_dir-Wechsel: HuggingFace's Cache-Layout dedupliziert via Symlinks zwischen blobs/ und snapshots/; ohne Symlinks dupliziert local_dir-Mode die Modell-Dateien physisch. Plus die uv-venv-Größe (torch CPU ~ 1.0 GB) summiert sich zu ~1.9 GB. Aktuell akzeptiert — APPROX_DISK_USAGE_MB-Konstante in der CLI sollte in einem Follow-Up auf 1900 erhöht werden, ebenso die Spec-Angabe in §5.3.

§MManueller Lifecycle-Test (Step-by-Step)

Vollständiger End-to-End-Smoketest: install → status → classify-files → merge → uninstall. Alle Schritte cross-platform; in strict-mode-Projekten muss jedem Bash-Aufruf redactor wrap -- vorangestellt werden (siehe Hinweise pro Block).

Strict-Mode-Hinweis

Wenn dieses Repo / Projekt redactor-Hooks aktiv hat (.claude/settings.json mit bash-strict), jeden $ <cmd>-Block unten als $ redactor wrap -- <cmd> ausführen. Beispiel: redactor wrap -- redactor classifier-install --quiet. Sonst direkt.

M.1 Prerequisites prüfen

# uv muss installiert + auf PATH sein (kein pip-Fallback)
uv --version
# → uv 0.11+ erwartet (Windows: winget install --id astral-sh.uv)

# Redactor muss 0.7.0+ sein
redactor --version
# → redactor 0.7.0

# Aktueller Classifier-Stand (sollte "no" überall sein, frischer Start)
redactor classifier-status

M.2 Installation

# Installiert venv + ML-Deps + Models. Dauer: ~3-10 min je nach Netz.
# --quiet überspringt den Disk-Confirm-Prompt.
redactor classifier-install --quiet

M.5 Classifier laufen lassen

# Default (Text-Output, Threshold 0.6, schreibt nach ~/.redactorignore.suggested)
redactor classify-files "$TEST"

# Mit niedrigerem Threshold (sieht mehr) + custom Output-Pfad
redactor classify-files "$TEST" \
    --threshold 0.3 \
    --output "$TEST/out.suggested"

# JSON-Format für agent-pipelines
redactor classify-files "$TEST" \
    --threshold 0.3 \
    --format json \
    --output "$TEST/out.suggested.json"

# YAML-Format
redactor classify-files "$TEST" \
    --threshold 0.3 \
    --format yaml \
    --output "$TEST/out.suggested.yaml"

# Mit max-file-size und max-depth eingrenzen (für große Trees)
redactor classify-files ~/Documents \
    --threshold 0.6 \
    --max-depth 3 \
    --max-file-size 10MB \
    --output ~/.redactorignore.suggested

M.7 Merge in ~/.redactorignore

# Dry-run zuerst — zeigt was passieren würde, schreibt nichts
redactor classify-merge "$TEST/out.suggested" --dry-run

# Interaktiv: y/n/s(skip rest)/q pro Vorschlag
redactor classify-merge "$TEST/out.suggested"

# Non-interaktiv: alle Vorschläge übernehmen (vertraut der ML)
redactor classify-merge "$TEST/out.suggested" --yes

# Resultat: ~/.redactorignore wird angehängt mit den akzeptierten Pfaden
cat ~/.redactorignore | tail -20
