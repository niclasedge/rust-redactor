§0Motivation & Zielbild

v0.7 hat .redactorignore (gitignore-style Pfade + Keywords) und den ML-Classifier (Path-Block-Vorschläge) eingeführt. Beim echten Einsatz haben sich vier konkrete Lücken gezeigt:

  1. Classifier produziert nur Pfade, keine Keywords. Personennamen, Codenamen und ähnliches müssen manuell gepflegt werden — der zweitwichtigste Use-Case (Keywords aus PII-Hits ableiten) ist ungelöst.
  2. Jeder classify-files-Lauf ist Full-Scan. Bei 5000 Files in ~/Documents dauert das jede Iteration neu — der User sieht außerdem dieselben bereits abgelehnten Vorschläge wieder und wieder.
  3. Pattern-Coverage hat Gaps: auth.psd1 mit ClientId/TenantId kommt teilweise durch, OneDrive-Pfade auf .pfx-Dateien werden im Bash-Output nicht voll-maskiert, Windows-Usernames in C:\Users\… bleiben sichtbar.
  4. Debugging-Lücke: Wenn etwas geblockt wird, sieht man nicht, welche Regel oder welche Zeile in .redactorignore den Block ausgelöst hat. Erschwert das Erkennen von Over-Blocking.

Dieses Spec adressiert alle vier in zwei Phasen.

Leitlinie für dieses Spec

Additiv, nicht destruktiv. Phase 6 erweitert den Classifier um Keyword-Stream + State-File, ändert aber nichts an der bestehenden Pfad-Logik. Phase 7 fügt fehlende Patterns hinzu, ohne existierende zu ändern. Niemand muss sein .redactorignore migrieren.

§1Befunde aus echtem Einsatz

#SymptomReproduktionUrsache
F1 Bei einem OneDrive-Pfad mit .pfx im Bash-Output wird nur das Firmen-Keyword im Pfad maskiert. Das .pfx-File selbst (Filename + Pfad) bleibt komplett lesbar. Output von ls "OneDrive - <Firma> SE/Zertifikate/" zeigt vollständig Pfade wie cert-prod.pfx, backup.pfx — Pre-Tool-Block greift nicht, weil der Command-String auf den Ordner zeigt, nicht auf die .pfx-Datei. match_crypto_container greift nur, wenn der Command-String selbst die Crypto-Endung enthält. Files im Output durchlaufen Pattern-Mode-Redaktion, der hat aber keine Regel für „Pfade auf Crypto-Extensions".
F2 auth.psd1 mit ClientId / TenantId geht (teilweise) durch. PowerShell-Hash-Tabelle mit ClientId = '...' wird matched, aber Varianten ohne GUID-Format oder mit anderen Feldnamen (ApplicationId, CertificateThumbprint) entkommen. Außerdem: .psd1 ist heute nicht in Office-Doc-Defaults oder Crypto-Liste. Pattern azure_cred_guid deckt 6 Feldnamen ab, GUID-Werte. PSD1-Files können aber beliebige Credentials enthalten (Thumbprints, Secrets, App-Names). Kein structural Mode für .psd1, keine Type-Detection.
F3 C:\Users\Alice\… bleibt im Output sichtbar — Username ist personenbezogen. Jeder File-Listing, jede Stack-Trace, jeder Pfad-Output enthält den Windows-Username. Keine Pattern-Rule für „Home-Dir-Path" oder „Username". Der Path-Guard blockt Lese-Zugriffe, redacted aber den Username nicht in Output-Streams.
F4 Path-Guard ist zu aggressiv: grep -E "\.pfx" wird geblockt, obwohl .pfx nur als Regex-Pattern auftaucht, nicht als Pfad-Argument. Real beobachtet bei der Entwicklung dieses Specs: grep -nE "\.pfx" src/hook.rs → refused — command touches a crypto container. Substring-Match auf .pfx im command-string ohne Kontextprüfung (Quoting, Position nach Regex-Flags, Existenz des Files).
F5 Wiederholte Vorschläge: nach classify-merge mit „no" werden im nächsten Run dieselben Files wieder vorgeschlagen. Jeder classify-files ~/Documents-Lauf produziert identische .suggested-Liste (außer es kommen neue Files hinzu). Kein State-File. Classifier kennt keine Decision-History.
F6 Keine Keyword-Vorschläge. classify-files schreibt ausschließlich Pfade in .suggested. Personennamen / Firmennamen aus PII-Hits müssen manuell aus der evidence-Zeile gepflückt werden. YAGNI-Entscheidung aus v0.7-Spec („Modus 1 reicht"). Realer Einsatz zeigt: Modus 2 ist komplementär nötig.

Decision-Werte

  • accepted — in ~/.redactorignore übernommen → skip in folgenden Läufen (außer --reconsider-accepted)
  • rejected — User hat „no" gesagt → skip (außer --reconsider-rejected)
  • pending — in .suggested, noch nicht reviewed → wird nicht erneut vorgeschlagen, bleibt aber im File
  • null / fehlt — noch nie klassifiziert → wird verarbeitet

6.3 Keyword-Extraktion — Filter-Pipeline

GLiNER produziert pro File typischerweise 0-50 Entities. Ohne Filter wäre .keywords.suggested Müll. Die Pipeline filtert in drei Stufen:

flowchart TD E["GLiNER Entities
(text, label, score)
pro File"] --> F1{"label ∈ {PERSON,
ORGANIZATION,
EMAIL, LOCATION}?"} F1 -->|"nein"| Drop1["drop"] F1 -->|"ja"| F2{"score ≥ 0.85?"} F2 -->|"nein"| Drop2["drop"] F2 -->|"ja"| F3{"len ≥ 3 Zeichen
& nicht reine Ziffern?"} F3 -->|"nein"| Drop3["drop"] F3 -->|"ja"| Agg["aggregiere über alle Files"] Agg --> F4{"occurrence_count
in ≥ 2 distinct files?"} F4 -->|"nein"| Drop4["drop"] F4 -->|"ja"| F5{"bereits in
~/.redactorignore?"} F5 -->|"ja"| Drop5["drop (dedup)"] F5 -->|"nein"| Out["→ .keywords.suggested"]

Begründung der Filter-Schwellen

FilterSchwelleWarum
Entity-Type PERSON, ORGANIZATION, EMAIL, LOCATION Wiederverwendbar über Files. TAX_NUMBER / IBAN / PHONE sind file-spezifisch → bleiben im Pfad-Stream.
Min-Score 0.85 Strenger als Path-Stream (0.6) — Keywords wirken global, falsche Positives sind teurer.
Min-Länge 3 Zeichen, nicht ausschließlich Ziffern Verhindert Initialen / Hausnummern als Keywords.
Min-Occurrence ≥ 2 distinct files Wichtigster Filter. Eine PERSON in einem File = wahrscheinlich Zufall. Dieselbe Person in 3 Files = relevant.
Dedup case-insensitive gegen ~/.redactorignore Vermeidet doppelte Einträge bei Re-Scans.

6.4 CLI-Erweiterungen

# Inkrementell (Default): nur unbekannte / geänderte Files
redactor classify-files ~/Documents

# Force-Full-Scan
redactor classify-files ~/Documents --force

# Nur Files, die in den letzten 30 Tagen modifiziert wurden
redactor classify-files ~/Documents --since 30d

# Auch früher abgelehnte Files nochmal anbieten
redactor classify-files ~/Documents --reconsider-rejected

# Nur eine Output-Sorte
redactor classify-files ~/Documents --paths-only
redactor classify-files ~/Documents --keywords-only

# State-Datei inspizieren / aufräumen
redactor classify-state show                    # human-readable Tabelle
redactor classify-state show --format json
redactor classify-state prune                   # entfernt Einträge zu nicht-existenten Files
redactor classify-state forget <path-or-keyword>  # löscht eine Decision (sodass sie wieder vorgeschlagen wird)

# Merge erweitert
redactor classify-merge --paths    ~/.redactorignore.suggested
redactor classify-merge --keywords ~/.redactorignore.keywords.suggested
redactor classify-merge --all      # beide hintereinander

6.5 Workflow: erster vs. wiederholter Lauf

Erstlauf (Cold State)

# 5000 Files in ~/Documents
$ redactor classify-files ~/Documents
walking 5000 files...
  4823 candidate files (177 skipped: hidden/symlinks/binary)
  4823 to classify (state empty)
classifying via sidecar (~25 min)...
  342 path-suggestions written
  18  keyword-candidates written
  state.json: 4823 entries

$ redactor classify-merge --all
  342 paths to review →    [y/n/s/q]
  18  keywords to review → [y/n/s/q]

$ redactor classifier-state show
  total: 4823 / accepted: 87 (paths) + 12 (keywords) /
  rejected: 255 (paths) + 6 (keywords) /
  pending: 0

Folgelauf (Warm State)

# 5 Wochen später, 47 neue Files + 12 geändert
$ redactor classify-files ~/Documents
walking 5000 files...
  4953 candidates (current scan)
  4847 unchanged (skip via hash-cache)
  47   new files
  12   modified files (hash mismatch)
  → 59 to classify
classifying (~30 sec)...
  4 path-suggestions, 1 keyword-candidate

$ redactor classify-merge --all
  4 paths to review → [y/n/s/q]
  1 keyword to review → [y/n/s/q]

Latenz-Effekt

Cold-Run: 5000 Files × ~300 ms = ~25 min. Warm-Run mit nur Hash-Check: 5000 × ~5 ms = ~25 sec. Klassifikation nur für die 59 neuen/geänderten = ~30 sec. Faktor ~50× schneller bei typischem Inkrement.

§3Format-Diskussion: JSON vs. gitignore-style

Frage: soll .redactorignore selbst JSON werden? Oder zumindest .suggested?

3.1 Trade-Off-Matrix

Aspektgitignore-style (heute)JSON
Mit der Hand editierbarJA — vertraute SyntaxUMSTÄNDLICH — Quoting, Kommas, keine Comments
Comments + Provenanceeingeschränkt — nur als #-Lines davorJA — strukturierte Felder pro Eintrag
Tooling (Diff, Merge in git)JA — line-based diffsSCHLECHT — JSON-Diffs sind unleserlich
Programmatische AnalysePARSING nötig (Heuristik Keyword vs. Pfad)TRIVIAL
Verbosity1 Zeile pro Eintrag5-8 Zeilen pro Eintrag (mit Metadaten)
Validierungnicht möglichJSON Schema

3.2 Empfehlung: Hybrid mit klarer Trennung

Drei Files, drei Formate, drei Verantwortlichkeiten:

FileFormatWer schreibtWer liest
~/.redactorignore gitignore-style (unverändert) Mensch + classify-merge (append-only) Hook-Runtime (jeder Tool-Call)
~/.redactorignore.suggested
~/.redactorignore.keywords.suggested		 Default: gitignore-style mit #-Metadaten
Optional: --format json		 classify-files classify-merge + Mensch (Review)
<config>/classifier/state.json JSON (immer) classify-files + classify-merge classify-state + interne Logik

Warum nicht JSON für .redactorignore selbst?

  • Editier-Frequenz: Der Mensch fasst .redactorignore mehrmals pro Woche an (Keywords ergänzen). Comments sind dort essentiell („# Kunde X — seit 2024-03"). JSON würde diese UX kaputtmachen.
  • Hook-Latenz: JSON-Parsing pro Tool-Call wäre zwar nicht langsam, aber die gitignore-Heuristik ist deterministisch und cached schon im Path-Guard.
  • Git-Diff-Lesbarkeit: Ein PR „add 3 keywords" ist als gitignore-Diff sofort verständlich, als JSON-Diff frickelig.

Existiert heute schon, sollte aber das neue Hybrid-Schema bekommen:

§4Provenance — welche Zeile blockt was?

Heute: wenn ein File geblockt wird, sagt der Hook was geblockt wurde („path is on the user's .redactorignore list"), aber nicht welche Zeile oder welche Regel-Kategorie.

pub struct Match {

pub enum MatchSource {

§5Phase 7 — Pattern-Gaps füllen

Die drei Befunde F1/F2/F3/F4 aus §1 brauchen jeweils eigene Fixes. Klein und punktuell, keine Architektur-Änderung.

7.1 F1: Crypto-Container-Pfade auch im Text-Output maskieren

Problem

match_crypto_container blockt Pre-Tool, aber Output-Streams (ls-Listing eines Ordners) zeigen .pfx-Pfade als gewöhnlichen Text.

Fix

Neue Pattern-Rule in patterns.rs::defaults():

("crypto_container_path",
 r"(?i)[/\\][^/\\\s'\"]+\.(kdbx|kdb|gpg|pgp|asc|age|p12|pfx|keychain-db|pem|key)\b",
 "<redacted:crypto_container_path>"),

Matcht Pfad-artige Tokens, die mit Crypto-Extension enden, und ersetzt den ganzen Pfad (nicht nur die Extension). Pattern-Mode in Bash-Output greift dann auch.

Tests

  • Positive: cert-prod.pfx, /Users/x/vault.kdbx, C:\…\backup.gpg
  • Negative: example.com, Wort „pfx" ohne Pfad-Kontext
  • Edge: Pfad mit Spaces in OneDrive-Pfaden — eventuell zwei-Pass-Strategie

7.2 F2: PSD1 / PowerShell-Credentials breiter abdecken

Problem

auth.psd1 kann beliebige Felder enthalten: ApplicationId, CertificateThumbprint, ClientSecret, Username, Password. Aktuelle Patterns decken nur 6 Azure-GUID-Felder ab.

Fix — drei Schichten

  1. Pattern-Erweiterung in defaults(): 
    // Erweiterte Azure / Entra ID Felder
("azure_cred_guid_extended",
 r#"(?i)(TenantId|ClientId|AppId|ApplicationId|ObjectId|SubscriptionId|DirectoryId|PrincipalId)["']?\s*[:=]\s*["']?[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}["']?"#,
 "$1=<redacted:azure_guid>"),

// CertificateThumbprint (SHA-1 hex)
("cert_thumbprint",
 r#"(?i)(CertificateThumbprint|Thumbprint|FingerPrint)["']?\s*[:=]\s*["']?[0-9A-Fa-f]{40}["']?"#,
 "$1=<redacted:cert_thumbprint>"),

// Generic Secret-Field-Heuristik für PowerShell
("ps_secret_field",
 r#"(?i)(ClientSecret|ApiKey|AccessKey|Token|RefreshToken|Password|Secret|PSCred)\s*=\s*["'][^"']{8,}["']"#,
 "$1=<redacted:ps_secret>"),
  2. Structural-Mode für .psd1: Wie heute für .env — Read-Tool blocken, forcen auf redactor --type psd1 <file>. Neuer Mode in redactor.rs::Mode::PowerShellData mit AST-Light-Parser (Schlüssel-Wert-Paare), Values immer <redacted>.
  3. Optional: .psd1 in Path-Guard-Default aufnehmen wenn der Filename einem auth|cred|secret|key-Muster folgt — analog zu .env-Familie.

7.3 F3: Username / Home-Dir-Path automatisch maskieren

Problem

C:\Users\Alice\… und /home/alice/… leaken den Username — personenbezogen, in jedem Pfad-Output sichtbar.

Fix — dynamisches Pattern aus env

Beim Start: aktueller Username aus env lesen, in eine Runtime-Pattern-Rule rein-compilen.

fn dynamic_username_rule() -> Option<Rule> {
    let username = std::env::var("USERNAME")              // Windows
        .or_else(|_| std::env::var("USER"))               // Unix
        .ok()?;
    if username.len() < 2 { return None; }                // skip super-short

    // Match in path-context, case-insensitive
    let re = format!(
        r"(?i)([/\\])({})([/\\])",
        regex::escape(&username)
    );
    Some(Rule {
        name: "current_username",
        regex: re,
        replacement: "$1<redacted:username>$3".to_string(),
        // origin: dynamic, env-derived
    })
}

Plus: explizite Home-Dir-Rule

// Windows Home-Dir-Pattern (matched auch fremde Usernames)
("windows_home_dir",
 r"(?i)C:[\\/]Users[\\/]([^\\/\s'\"]+)",
 "C:\\Users\\<redacted:username>"),

// Unix Home-Dir-Pattern
("unix_home_dir",
 r"(?:^|[\s'\"])/(?:home|Users)/([^/\s'\"]+)",
 "/home/<redacted:username>"),

Trade-Off

Username-Maskierung führt zu unleserlichen Outputs in find-/ls-Resultaten — der LLM sieht statt C:\Users\niclas.edge\Documents\foo nur noch C:\Users\<redacted:username>\Documents\foo. Für die meisten Tool-Calls OK, in Pfad-Operationen aber relevant. Empfehlung: Default ON, opt-out per Config ([policy] mask_username = false).

7.4 F4: Path-Guard-Smartness — nicht bei Pattern-Literalen blocken

Inhalt wie unten — danach folgen die brainstorming-getriggerten Sub-Phasen 7e–7i (siehe §B).

Problem

grep -E "\.pfx" wird geblockt, obwohl .pfx nur als Regex-Literal nach -E auftaucht.

Fix

Im Pre-Bash-Hook: vor dem Substring-Match parsen, ob das Token im Argument-Kontext eines bekannten Pattern-Flags steht:

fn extract_path_tokens(cmd: &str) -> Vec<&str> {
    // Tokenize (respecting quotes), then filter out arguments that
    // immediately follow a "pattern-only" flag like -E / -e / --regex /
    // -P (grep family) or --grep (git family).
    let tokens = shlex::split(cmd)?;
    let mut paths = Vec::new();
    let mut skip_next = false;
    for tok in &tokens {
        if skip_next { skip_next = false; continue; }
        if matches!(tok.as_str(), "-E" | "-e" | "-P" | "--regex" | "--grep" | "--include" | "--exclude") {
            skip_next = true;          // next token is a pattern, not a path
            continue;
        }
        paths.push(tok);
    }
    paths
}

Plus: optional File-Existenz-Check vor dem Block — wenn der Token nicht im Filesystem auflösbar ist, ist es vermutlich kein Pfad-Touch. Aber: Risiko von TOCTOU-Race. Daher als Heuristik nur in Kombination mit Token-Position.

Tests

  • grep -E "\.pfx" file.txt → nicht blocken (Pattern-Literal)
  • grep "x" cert.pfx → blocken (Crypto-Container in Argument)
  • cat /Users/x/vault.pfx → blocken (direkter Pfad)
  • echo "vault.pfx ist ein File" → Edge-Case, vermutlich nicht-blocken (echo-Argument, kein File-Touch)

§6Future / kleine Optimierungen

Sammelliste — nichts davon ist in Phase 6 oder 7 enthalten, alles als kleinerer Follow-up.

§DEntscheidungs-Log

D-1 — Hybrid (Pfade + Keywords), nicht Ersatz

Keywords ergänzen Pfade, ersetzen sie nicht. Pfad-Blocks bleiben für file-spezifische PII (Steuernummer, IBAN), Keywords für wiederverwendbare Tokens (PERSON, ORG, EMAIL). Begründung: jede File-spezifische Information als globales Keyword zu setzen führt zu Over-Redaction; jeden Personennamen file-by-file zu blocken skaliert nicht.

D-2 — SHA256-Hash-Cache als Default-Strategie für Inkrementalität

~10 ms pro File auf SSD. Bei 5000 Files = 50 sec — akzeptabel als „one-time per re-scan" vs. der Modell-Inference (~25 min). mtime-only war zweite Wahl; touch-Resistance nicht wichtig genug für die User-Realität.

D-3 — gitignore-Format bleibt für ~/.redactorignore

JSON nur für state.json (Maschinen-State) und optional für .suggested (Agent-Pipelines). Mensch editiert gitignore-style, Maschine konsumiert JSON, beide gleichzeitig glücklich.

D-4 — Min-Occurrence ≥ 2 als wichtigster Keyword-Filter

Single-File-Hits sind statistisch Noise. Doppelte-File-Hits sind signal-stark. Verifizierbar mit Test-Korpus aus echtem ~/Documents (anonymisiert).

D-5 — Username-Maskierung default-on, opt-out per .redactor.toml

Personenbezogenes Datum, das in jedem zweiten Tool-Output auftaucht. Schaden bei Leak > UX-Nervigkeit bei Default-On. Opt-out für Pfad-intensive Projekte verfügbar.

§?Offene Punkte / TBD

  1. Hash-Algorithmus: SHA256 vs. xxhash3. SHA256 ist Standard, xxhash3 ist ~5× schneller. Da wir nicht crypto brauchen (nur Equality-Check), könnte xxhash3 ausreichen. Entscheidung in Phase 6a.
  2. Keyword-Entity-Type-Mapping aus GLiNER: GLiNER gibt Custom-Labels zurück (die User-Labels aus labels.txt). Wie kommen wir an die PRESIDIO-Entity-Typen (PERSON, ORG, EMAIL)? Möglicherweise Presidio's Built-in Recognizers parallel zu GLiNER laufen lassen, oder Label-Heuristik via Regex über Entity-Text.
  3. State-File-Locking: Was passiert bei parallelem classify-files? Atomic-write reicht für letzten-write-wins, aber sauberer wäre fcntl-Lock. Cross-Plattform-Locking ist Sonderfall.
  4. Migration von altem State (ohne v6) auf neuen: Erste classify-files-Lauf mit Phase-6-Binary sollte alten .suggested einlesen (wenn vorhanden) und in State übertragen — Decision = pending. Aufwand klein, aber muss bedacht werden.
  5. Pattern-Severity: Heute alle Patterns gleichwertig. Phase-8-Idee: Tiers (CRITICAL = Crypto-Key / API-Key, HIGH = PII, MEDIUM = Username / Host, LOW = generischer Identifier). Logging + UI-Hint könnten davon profitieren.
  6. Username-Pattern-Konflikt: Wenn der Username „Niclas.Edge" auch Teil legitimer Strings ist (sehr unwahrscheinlich, aber denkbar), führt die Maskierung zu False-Positives. Empirisch in Phase 7c beobachten.

B.2 Keyword-Normalisierung & Dedup

Klarstellung vom User für Phase 6b:

  • Storage: Keywords werden bei automatischem Append durch classify-merge als lowercase in ~/.redactorignore geschrieben.
  • Match-Verhalten: case-insensitive (existiert bereits via (?i)-Regex-Prefix).
  • Dedup: vor dem Append wird case-insensitive gegen alle existierenden Keywords verglichen. "Niclas Edge", "niclas edge", "NICLAS EDGE" zählen als ein Keyword.
  • Manuelle Edits respektieren: bestehende Einträge im File, die User manuell mit Mixed-Case eingegeben hat, werden NICHT normalisiert (nur bei Classifier-Auto-Append).
fn normalize_for_storage(text: &str) -> String {
    text.trim().to_lowercase()
}

fn is_duplicate(candidate: &str, existing: &[String]) -> bool {
    let cand = candidate.trim().to_lowercase();
    existing.iter().any(|e| e.trim().to_lowercase() == cand)
}

M (~300 LOC, hängt vom Audit-Ergebnis ab)

Regex vs. GLiNER — Verteilung

Regex ist deterministisch, schnell, lückenlos — solange das Muster fest ist. GLiNER ist kontext-sensitiv, langsam, recall-getrieben — fängt Cases ab, die Regex nicht sehen kann. Beide laufen parallel:

  • Regex-Hits → direkt redacted in Tool-Output (Pattern-Mode in redactor.rs). Kein Vorschlags-Step nötig.
  • GLiNER-Entity-Hits (HOSTNAME/PASSWORD/SECRET) → in den Keyword-Vorschlag-Stream, weil sie kontext-abhängig sind und User-Review verdienen.

So bleibt Regex-Pipeline schnell (Auto-Redaction), und GLiNER bringt zusätzliche Recall für die Edge-Cases.
